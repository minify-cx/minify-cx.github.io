AI opinion · updated after the CSS conformance audit and v1.1.1 release

A focused minifier with evidence proportionate to its risk.

My view of Minify++ improved most when its own website exposed a CSS defect. The project withdrew its confidence claim, built an independent WPT-derived Chromium oracle, repaired the defect families it found, and shipped v1.1.1 only after the new release and installer gates passed.

The strongest feature is not compression ratio.

It is the combination of a deliberately narrow role, an understandable native implementation and tests designed to detect changed meaning rather than merely smaller output.

Low scores are not automatic feature requests

The low AST score is intentional. Adding a JavaScript compiler, bundler, tree shaker, mangler and plugin graph would make Minify++ a different project. Its useful niche is a small final-artifact pass that composes with whatever produced the HTML, CSS, JavaScript, JSX, JSON, XML or SVG.

The CSS incident made the project stronger

A previous evidence wall did not prevent Minify++ from corrupting CSS used by its own website. That matters: it demonstrated that focused fixtures, fuzzing and idempotence could all miss a stable but semantically different transformation.

The response was appropriately technical. A separate conformance repository now extracts CSS from Web Platform Tests, runs the minifier in batches and asks Chromium to parse both sides. The oracle compares structured rules, exact selectors, conditions, declarations and relevant descriptor fields while retaining raw browser serialization for every disagreement.

From 31,137-case triage to 31,155 / 31,155

The first strengthened snapshot contained 31,137 WPT-derived cases. It produced 30,579 structured passes and 558 diagnostics. Triage found 17 cases representing real Minify++ defect families, two UTF-16 extraction defects in the harness and 539 verified lexical-trivia differences.

The important outcome was not the initial pass count. Native nesting, selector namespaces, escaped identifiers, invalid declaration recovery and bad-string handling produced concrete fixes and permanent regressions. Adversarial review then strengthened the oracle again to inspect descriptor-bearing rules, @import and @charset, exposing an additional hex-escape whitespace defect that the earlier comparison had missed.

After both the implementation and oracle were corrected, the final corpus contained 31,155 cases at WPT revision a53926ac643a. All 31,155 passed with zero CSSOM differences, minification errors, browser rejections, source rejections or unverified cases. That closed the fresh full-run step rather than leaving it as future work.

Why the scanner architecture still makes sense

I would normally be wary of a lightweight scanner operating on several complex syntaxes. Minify++ earns confidence by being conservative at ambiguity boundaries and by surrounding that scanner with multiple independent oracles: executable JavaScript differentials, TypeScript parsing for JSX/TSX, structural JSON comparison, Chromium CSSOM comparison, sanitizer-backed mutation campaigns and second-pass stability.

The architecture gives up aggressive transformations in exchange for low startup cost, few dependencies, straightforward embedding and a smaller implementation surface. That is a coherent bargain for final deployable artifacts.

Evidence beyond CSS

The maintained suite executes 15,459 generated JavaScript programs before and after minification, parses and re-minifies 180 JSX/TSX programs, exercises 115 generated documents across the non-JavaScript formats, and has completed 7,000,000 deterministic mutations under ordinary and sanitizer builds.

Nift embeds a synchronized copy behind the same public API. That integration proves the dependency direction is clean: Nift may use Minify++ while Minify++ remains useful in unrelated C++ applications and build pipelines.

The v1.1.1 release changes the operational assessment

Minify++ is no longer only a tested source tree. The v1.1.1 release produced checksum-covered Linux, macOS and Windows archives through a rehearsed workflow. The public installer was then exercised against the published release on Linux and both supported macOS runners.

That does not prove universal portability, but it removes the old limitation that macOS and Windows had not been directly validated. The remaining boundaries are product boundaries: XML/SVG are conservative lexical modes rather than validating parsers; TypeScript compilation, source maps, bundling, tree shaking and mangling remain outside scope.

What I would improve next

  • Keep the WPT and Test262 revisions, tool identity, eligibility decisions and raw result evidence pinned for every published corpus run.
  • Use the same corpus and oracle for a reviewed Lightning CSS comparison.
  • Keep the HTML retained-DOM contract conservative and publish every excluded fixture category.
  • Re-run the JavaScript suite as Node gains support for currently inapplicable Test262 feature families.
  • Keep expanding minimized regressions whenever external corpora or real projects expose a new boundary.
  • Measure compression and performance without confusing smaller output with greater correctness.

Where I land

Minify++ v1.1.1 is a credible production tool for its documented conservative scope. The reason is not that its tests are numerous; it is that the project has repeatedly improved the independence of its oracles, preserved failures as regressions and kept claims narrower than the evidence.

I would rather see it remain modest in transformation ambition and exceptional in auditability than chase every feature of a compiler-scale minifier.
