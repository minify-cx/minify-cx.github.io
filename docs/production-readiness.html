Production assessment · updated after the CSS conformance audit and v1.1.1 release

Is Minify++ production-ready?

Yes, for its documented role as a conservative final-artifact minifier. That assessment now rests on browser-backed CSS conformance work, semantic and parser differentials across the other formats, sanitizer-backed mutation testing, synchronized Nift integration and published cross-platform release artifacts.

Production-ready within the documented contract.Minify++ is suitable when a build needs small, dependency-light native minification without handing the tool responsibility for compilation, bundling or AST-level optimization.

Why the answer is yes

  • The audited CSS conformance snapshot covered 31,137 WPT-derived cases through Chromium's parser and structured CSSOM.
  • The audit exposed 17 browser-relevant cases representing real defect families in selector whitespace, escapes and error recovery; those families were repaired and retained as focused regressions.
  • The CSS harness distinguishes structural changes from harmless browser serialization differences and preserves raw diagnostics for review.
  • 15,459 generated JavaScript programs execute before and after minification with equivalent observed behavior.
  • 180 JSX/TSX programs pass reference parsing and second-pass checks.
  • 115 generated non-JavaScript documents exercise the supported HTML, CSS, JSON, XML and SVG contracts.
  • 7,000,000 deterministic mutations pass across all seven format modes under ordinary and ASan/UBSan builds.
  • The standalone and Nift-embedded implementations pass an exact 20-file synchronization gate.
  • make distcheck validates a clean committed source archive rather than relying on an already-built working tree.
  • Version 1.1.1 is distributed as checksum-covered Linux, macOS and Windows archives through the rehearsed release workflow; the public shell installer was exercised against the published release on Linux and supported macOS runners.

What the CSS conformance work changed

The earlier test wall was strong enough to find many scanner errors, but it still missed a real stylesheet corruption. The response was to add an independent oracle rather than simply add one more fixture. The conformance lab extracts CSS from Web Platform Tests, minifies it in bounded batches, then asks Chromium whether the original and transformed stylesheets produce the same structured rules, selectors, conditions, declarations and descriptors.

In the audited pre-final-repair snapshot, 30,579 of 31,137 cases passed the structured comparison. Of 558 diagnostics, 17 exposed real Minify++ defects, two exposed UTF-16 extraction defects in the harness, and 539 reduced to verified lexical-trivia differences. There were no minifier errors or browser/source rejections in that snapshot.

The site does not claim 31,137/31,137.

A fresh full run of the corrected implementation and revised oracle is still required before publishing a new all-cases result. The value of the completed audit is the independent methodology, the defects it found and the permanent regressions produced from them.

Evidence is deliberately layered

No single test establishes that a minifier preserves meaning. Minify++ therefore combines several different failure oracles:

  • Execution: generated JavaScript is run before and after transformation.
  • Reference parsers: JSX/TSX and structured formats are checked through independent parsers.
  • Browser semantics: Chromium CSSOM comparisons catch stable but meaning-changing CSS output.
  • Mutation and sanitizers: malformed and adversarial inputs attack crashes, hangs, unbounded growth and unsafe memory behavior.
  • Second-pass acceptance: successful output must remain inside Minify++'s own supported language.
  • Packaging and integration: clean archives, published installers and the Nift synchronization gate exercise the code as users consume it.

Known boundaries

  • Not a compiler or bundler: Minify++ does not compile TypeScript or Sass, resolve module graphs, tree-shake, mangle symbols or perform AST-level optimization.
  • HTML: raw script/style bodies and embedded template content are preserved rather than recursively transformed. A corpus-backed HTML conformance program is a sensible next evidence layer.
  • XML/SVG: these are conservative lexical modes, not complete validating XML processors.
  • TypeScript: there is no general TypeScript input mode. TSX-aware JSX boundaries do not amount to TypeScript compilation.
  • Finite evidence: large external corpora and mutation campaigns increase confidence but cannot prove correctness for every future grammar extension.
  • Performance: published measurements are repeatable regression references for their stated hosts and fixtures, not universal throughput promises.
  • Filesystem durability: staged in-place replacement protects against ordinary write failures but does not claim power-loss durability or preservation of every filesystem metadata field.

What would change this assessment?

A supported input changing meaning, a crash, hang or unbounded-growth case, an unexplained corpus regression, drift between the standalone and Nift-embedded copies, unsafe file replacement, a failed clean-package gate, or public claims expanding beyond tested behavior would all require the assessment to be revisited.

The candid conclusion

Minify++ is production-ready because its scope is narrow, its transformations are conservative and its evidence uses independent semantic oracles where simple output checks are insufficient. The CSS conformance work made that conclusion more credible by finding real faults and turning them into durable tests; it did not turn a finite corpus into a universal guarantee.
